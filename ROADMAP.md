# Lane Roadmap

Progress scale:

- `0` Not planned yet
- `1` Idea sketched
- `2` Narrow implementation exists
- `3` Useful but incomplete
- `4` Works for common cases
- `5` Works in full generality

| Feature axis | Progress | Current state | Next milestone | Full-general target |
| --- | ---: | --- | --- | --- |
| Operator-reference declarations | 3 | `Hom(A x A, A) &+ = f` style declarations are implemented for the current operator set. | Finish parser/tooling consistency for every accepted spelling, including `&(op)` where useful. | Every operator overload is declared through ordinary function signatures and resolves like any other overloaded function. |
| Category inference from operators | 3 | Categories can be inferred from required operator implementations in the supported cases. | Remove any remaining places that require explicit legacy category-constructor syntax. | Algebraic category membership follows entirely from available operator signatures and generated derived operations. |
| Legacy category constructors | 3 | Replacement syntax exists; legacy code should be deleted rather than preserved. | Remove remaining parser/typechecker/docs/tests paths for the old constructor syntax. | No legacy constructor syntax remains anywhere in compiler, tooling, docs, or tests. |
| Compiler/std split | 2 | Differential operators moved out of the Rust built-in registry and into explicit `#import std`; Rust-defined objects are now classified as core syntax or `std`-movable migration candidates. | Move one classified `std`-movable family from Rust into `std` and keep imports explicit. | Compiler only provides minimal syntax, typechecking, overload/module machinery, directives, and backend hooks; constructible objects live in `std`. |
| Surface desugaring before semantic analysis | 2 | A preprocessing pass canonicalizes declaration-level operator/neutral names and operator-reference calls before typechecking; a typed postprocessor lowers custom operators, vectors, field access, and indexing to core calls that emission maps to GLSL syntax. Backend-core arithmetic still typechecks directly. | Move ordinary operator expressions onto callable helper overloads once built-in arithmetic is represented as ordinary overloads. | Semantic analysis sees only the minimal Lane core language; typed postprocessing maps core overload calls to backend syntax. |
| Derived algebraic operators | 2 | Some derivation logic exists, but accepted operators must also be emitted as real callable helpers. | Ensure every derived operator accepted by typechecking has matching emitted code. | Operators such as subtraction, negation, division, and inverse are generated from any sufficient generic primitive set. |
| Neutral literals | 4 | `0`, `1`, and `e` can become neutral elements in expected-type contexts; other literals cannot. | Keep ambiguity resolution deterministic and avoid broadening neutral coercions. | Neutral literals work uniformly for user-defined algebraic structures with no object-specific special cases. |
| Numeric widening | 4 | Only one-way widening is supported: `Bool -> Int`, `Bool -> Float`, and `Int -> Float`. | Keep reverse casts rejected and make diagnostics clear. | Numeric inclusions remain minimal, predictable, and independent from algebraic scalar inclusion. |
| Scalar inclusion into unital algebras | 1 | Desired behavior is identified, but no final implementation should be added until it can be generic. | Prototype the simple retry heuristic: if an algebraic expression fails, insert `1` for the target algebra and retry through ordinary multiplication overloads. | Scalar inclusion works for any user-defined unital algebra through existing operators, not through named built-in special cases. |
| User-defined complex numbers | 3 | `C` is declared in `modules/complex.lane` as an ordinary Lane product/category type with its algebraic operations in the module. | Remove the remaining generic gaps exposed by the module version, especially derived division and point-free helpers for coordinate formulas. | Complex numbers are ordinary Lane definitions; compiler logic that works for complex also works for any equivalent user-defined algebra. |
| Built-in algebraic object removal | 1 | Some concrete algebraic objects still have compiler/emitter special cases. | Replace one concrete special case at a time with Lane definitions or generic operator lowering. | Compiler contains no new object-specific algebra logic; algebraic behavior lives in Lane code or generic lowering. |
| Operator syntax in editor tooling | 3 | Tree-sitter/LSP were updated for recent operator-reference syntax work. | Keep parser artifacts, highlights, LSP diagnostics, and examples aligned after each syntax change. | Editor tooling accepts exactly the same language surface as the compiler and has no stale legacy grammar paths. |
| Generic overload resolution | 3 | Function/operator overloads work for many concrete cases, including deterministic handling for neutral ambiguity. | Reduce ad hoc tie-breaking and prefer stable generic ranking rules. | Overload resolution handles operators, ordinary functions, neutral literals, scalar inclusion, and derived operators uniformly. |
| Lane-first standard algebra modules | 2 | `std` now owns differential operators through module definitions; many algebraic definitions still live in Rust or built-ins. | Start moving algebraic helpers that do not require compiler syntax into `std`. | Standard algebraic structures are implemented in Lane unless impossible without raw GLSL or low-level backend support. |
| Concrete `C`/`H` algebra modules | 3 | `complex` and `quat` own `C`/`H` type declarations, neutral values, scalar multiplication, multiplication, inverse, and complex transcendental overloads as Lane code; `std` imports both modules. Division should come from generic derived-operator module machinery, not C/H-specific Rust branches or hand-written per-type overloads. | Express the universal `a / b = a * ~b` rule as generic Lane/std derivation once module generics can state the required operator constraints. | `C` and `H` are ordinary Lane module definitions or aliases; equivalent user-defined algebras need no compiler changes. |
| GLSL builtin exposure through modules | 1 | Rust still preregisters many GLSL builtins as globally visible Lane functions. | Represent builtin functions as backend intrinsics imported by `std` rather than always-present compiler names. | The compiler emits calls after typechecking but does not decide the public standard-library function surface. |
| Product/category operation generation | 2 | Emitter can synthesize product/category structs and operations for current categories. | Move synthesis out of ad hoc emitter code into a derivation/postprocess layer or std-backed templates. | Product/category operations are generated by generic Lane/std machinery, with Rust only supplying unavoidable backend hooks. |
| Monoid power implementation | 2 | `pow` over monoids is represented by a dedicated `ValueExpr::MonoidPow` and emitted as generated GLSL loop support. | Move monoid power into `std` as a raw GLSL/backend intrinsic template. | `pow` is just a library function/overload; compiler IR has no dedicated monoid-power node. |
| Projection and diagonal sugar | 2 | `p{i}` and `diag{n}` are represented as special `FunctionExprKind` variants during typechecking. | Lower projection/diagonal syntax into ordinary core calls as early as type information allows. | Function expressions use ordinary calls/composition; projection/diagonal notation is surface sugar only. |
| Array helper functions | 2 | `size` and `concat` are special-cased in value typechecking. | Keep compile-time `size` support explicit, but move `concat` toward ordinary core/std function handling. | Array helpers are either core intrinsics with a tiny contract or std functions, not ad hoc parser/typechecker branches. |
| Object primitive/operator migration | 1 | Primitive and object-operator semantics still live mostly in Rust registry/emitter logic. | Move one object operator at a time into Lane module code using raw GLSL templates where needed. | Object constructors/combinators are imported definitions; Rust only knows the object evaluation boundary. |

## Partial feature examples

Each partially-complete feature should keep one example that works today and one example that describes the intended final behavior. Update this section whenever a feature moves along the progress scale.

| Feature axis | Works now | Not yet / final target example |
| --- | --- | --- |
| Operator-reference declarations | `Hom(A x A, A) &+ = f` declares addition for `A`; after that `a + b` typechecks for `A` values. | Every operator-reference spelling, including clarity forms such as `&(*)` or `&(+)`, should behave exactly like the corresponding generated overloaded function. |
| Category inference from operators | A user type with the required neutral and binary operator declarations can be recognized as supporting the matching algebraic operations. | Category membership should be inferred entirely from available operator signatures plus generated derived operators, with no explicit constructor fallback. |
| Legacy category constructors | New operator-reference declarations replace the old constructor-list direction. | Old constructor syntax should be absent from parser, typechecker, tests, Tree-sitter artifacts, docs, and examples. |
| Compiler/std split | `#import std` makes `derivative`, `gradient`, partials, `divergence`, `complex`, and `quat` available; `rust_defined_objects()` no longer lists `C`/`H` as Rust-defined built-in types. | More constructible objects should move to modules, leaving Rust only with grammar, directives, type machinery, imports, and backend hooks. |
| Surface desugaring before semantic analysis | `Hom(A x A, A) &+ = f` is canonicalized to the overloaded helper name before typechecking; typed postprocessing lowers pointwise `Hom(R, A) h = f + g` to `__add(f(_t), g(_t))` for custom `A`; vector and field/index forms lower to calls such as `__vec3(...)`, `__field_x(v)`, and `__index(xs, i)` before GLSL emission. | `a + b` should lower to the same core call as `__add(a, b)` before semantic analysis, including built-in arithmetic once it is represented as ordinary overloads. |
| Derived algebraic operators | Some operator availability can be recognized from related primitives. | If `+` and unary `-` exist, `-` should be emitted; if `*` and inverse exist, `/` should be emitted; every accepted derived operator must have real generated code. |
| Neutral literals | `0`, `1`, and `e` can become neutral elements in expected-type contexts such as `A zero = 0` or `G id = e`. | Neutral literals should work uniformly for all user-defined algebraic structures with deterministic ambiguity handling and no object-specific logic. |
| Numeric widening | `Bool -> Int`, `Bool -> Float`, and `Int -> Float` work; for example `R x = 1` and `R y = true` are allowed. | Reverse casts such as `Z n = 1.5` or `Z n = scalarR` should remain rejected, and diagnostics should explain the one-way inclusion clearly. |
| Scalar inclusion into unital algebras | No final generic implementation is committed; avoid adding named special cases for concrete objects. | If `S` has a unit and multiplication makes `A x S -> S`, then `s + a` should retry as `s + a * 1_S` through ordinary overloads. |
| User-defined complex numbers | `#import complex` declares `C` in Lane and supports expressions such as `z * w`, `~z`, `exp(z)`, and `pow(z, w)` without Rust type cases for `C`. | Equivalent user-defined algebras should be able to express the same derived division and scalar inclusion behavior through generic module machinery. |
| Built-in algebraic object removal | Some built-ins still have Rust-side support. | Each algebraic built-in should either become Lane module code or use generic compiler hooks that also work for user-defined types. |
| Operator syntax in editor tooling | Recent Tree-sitter/LSP work tracks the new operator-reference declarations. | Compiler, Tree-sitter, LSP diagnostics, formatter, examples, and installed Neovim parser should accept the same syntax with no stale legacy paths. |
| Generic overload resolution | Ordinary overloads and operator overloads work in common cases, including deterministic neutral-literal tie handling. | Overload resolution should uniformly rank ordinary overloads, operators, neutral literals, scalar inclusion retries, and derived operators. |
| Lane-first standard algebra modules | Differential operators are defined in `std` and use the compiler-injected `_lane_differential_epsilon`. | Algebraic definitions should live in Lane whenever possible; Rust should only provide raw backend primitives or genuinely impossible constructs. |
| Concrete `C`/`H` algebra modules | With `#import complex` or `#import quat`, `C`/`H` are module-declared nominal product types and `&*`, scalar `&*`, `1`, and `&~` are available from Lane definitions. | Generic division derivation should make `z / w` available from the universal rule `z * ~w` without C/H-specific Rust code or hand-written per-type overloads. |
| GLSL builtin exposure through modules | Functions like `sin` and `sqrt` are still globally available from Rust builtin overload tables. | `std` should import or define those names explicitly, while the compiler only treats them as backend intrinsics after overload resolution. |
| Product/category operation generation | Product/category declarations can synthesize GLSL support today. | The same synthesis should be expressed through generic derivation/std machinery rather than emitter-owned algebra rules. |
| Monoid power implementation | `pow(n, value)` works for supported monoids through generated GLSL loop code. | `pow` should become a std/backend-intrinsic overload instead of a dedicated semantic IR variant. |
| Projection and diagonal sugar | `p{0}` and `diag{3}` work in common function-expression contexts. | They should lower to ordinary projection/constructor calls before the semantic layer needs special expression variants. |
| Array helper functions | `size(xs)` and `concat(xs, ys)` work for statically known arrays. | `concat` should be an ordinary function/intrinsic, while `size` should have a minimal compile-time intrinsic boundary. |
| Object primitive/operator migration | Rust registry primitives like `Ball3D` and object ops like `union` work. | These should be std-imported object definitions/templates, leaving only the SDF object ABI in Rust. |
